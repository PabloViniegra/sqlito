# Product

<!-- impeccable:product-schema 1 -->

## Platform

terminal

## Users

Developers and data engineers who already live in a terminal and need to
inspect or modify local SQLite files. They open SQLito while debugging,
auditing schema, or scripting one-off queries, and they expect every
common operation to be reachable without leaving the keyboard.

## Product Purpose

Give that user a fast, terminal-native client for SQLite in which the
SQL is the interface. SQLito exists so that browsing, querying and
editing a local `.db` file feels as fluid as `psql` or `sqlite3` does
for fans of those CLIs, while looking and behaving as coherently as a
modern TUI (Claude Code, Lazygit). Success means the user never feels
friction between "I want to run SQL" and "I want to see the result";
the surrounding chrome is only there to keep them in flow.

## Positioning

SQLito is the terminal-native, keyboard-first answer for SQLite, with
the same kind of opinionated ergonomics Claude Code brings to its
domain. Its mechanism is concrete and defensible:

- A single synchronous engine (`better-sqlite3`) plus an Ink + React
  UI, so every interaction is sub-millisecond and the whole product
  is one runtime, not three.
- Inline outcome tags (`READ` / `WRITE` / `DDL` / `ERROR` / `PLAN`)
  classify intent in one syllable, independent of the SQL keyword and
  independent of theme, so logs and screenshots stay legible.
- The product explicitly _refuses_ scope: one DB at a time, SQLite
  only, no GUI. That refusal is the positioning — neighbouring tools
  either offer more (DB Browser, DataGrip) or less (raw `sqlite3`),
  and SQLito takes the middle by staying narrow and going deep.

## Operating Context

- Invoked from the shell as `sqlito <database.db>`; takes over the
  terminal via the alternate-screen buffer and restores prior content
  on exit.
- Persisted state lives under XDG paths (`~/.config/sqlito/config.json`,
  per-DB history, favourites).
- Designed for monospace terminals, with `Google Sans Code` as the
  preferred font; rendering assumes UTF-8 widths and `string-width`
  accounting.
- Ships with a sample database (`pnpm db:seed`) so a reviewer can run
  the full flow without bringing their own data.
- A 1500 ms cold-start budget is enforced by `pnpm bench` as a release
  gate.

## Capabilities and Constraints

**MVP shipped**

- Open a local SQLite file from CLI.
- Execute SQL synchronously through `better-sqlite3` with read-only
  detection and classified outcome tags.
- Render results in a windowed, viewport-aware table; PageUp/PageDown
  scroll past queries with an overflow indicator.
- Persistent per-DB query history with readline-style recall.
- Autocomplete for table and column names.
- CSV export (`.export <path>`) and clipboard copy (`.copy`) of the
  last result set.
- Dot-commands: `.tables`, `.schema [table]`, `.indexes`,
  `.set` / `.unset` / `.vars`, `.explain`, `.save` / `.run` /
  `.favorites` / `.forget`, `.theme`, `.help`, `.quit` (alias `.exit`).
- Readline editing inside the prompt: kill-to-start, kill-to-end,
  kill-word, word skip, multi-line wrap, history recall at boundary.
- Bracketed-paste support: multi-line paste inserts newlines without
  triggering Enter.
- Cold-start bench gate (`pnpm bench`) at 1500 ms.
- Command palette (Ctrl+P) over every dot-command.
- Switchable themes (`default`, `high-contrast`) persisted to XDG.

**Explicit non-goals**

- A GUI.
- Multiple concurrent database connections.
- Engines other than SQLite.
- A visual SQL editor.

**Open product decisions**

- The next roadmap item (per `PRD.md`) is _plugins_; shape and
  contract are undecided.

## Product Principles

1. **Keyboard first.** If a mouse would do it, the keyboard must do it
   first; if it cannot, the feature does not ship.
2. **SQL is the protagonist.** The chrome exists only to keep the user
   in flow; the prompt and the result are the page.
3. **One responsibility.** SQLite, one connection, no GUI. Refusing
   scope is a feature.
4. **Instant cold start.** Anything above the 1500 ms budget is a
   regression the bench will catch.
5. **Honest feedback.** Outcome tags and read-only detection make the
   blast radius of every statement legible before it runs.

## Accessibility & Inclusion

- Keyboard-only navigation is a primary, first-class contract — it is
  not a fallback, so users who cannot use a pointing device get the
  full product by default.
- Bracketed paste and readline editing match the conventions of
  terminal-literate users (including assistive tech that pipes input).
- Theme support is required, not decorative: `high-contrast` is
  shipped and persisted at the same level as the default.
